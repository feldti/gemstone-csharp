# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Projekt

- **Zweck:** Aufbau einer C#-Schnittstelle, um auf GemStone/S-Datenbanken zugreifen zu können (Wrapper über GemBuilder for C / GCI).
- **GemStone-Version:** 3.7.x (GemStone/S 64 Bit)

## Architektur

- `src/GemStone.Gci/Native/` — rohe Interop-Schicht, `internal`:
  - `GciNative.cs` — Einstiegspunkte als C#-Funktionszeiger (`delegate* unmanaged[Cdecl]<…>`), keine `[LibraryImport]`/`[DllImport]`. Der Grund: Unter .NET Framework gibt es keinen DllImport-Resolver, und die Datei heißt versioniert (`libgcirpc-3.7.5-64.dll`). Jede Funktion ist eine Wrapper-Methode mit verwalteter Signatur plus ein Feld `private static nint _Name`. Die Adresse holt `Fn(ref _Name, "Name")` beim ersten Aufruf. `BoolType` ist nativ `int` (`!= 0`), `const char[]` wird per `Utf8Z` + `fixed` als null-terminiertes UTF-8 übergeben. Neue Funktionen genau nach diesem Muster anlegen. Signaturen immer gegen `$GEMSTONE/include/gci.hf` prüfen, nicht nur gegen das Handbuch: `int` und `int64` bei Index- und Anzahl-Parametern unterscheiden sich je nach Funktion. Manche Namen sind Makros (`GciStoreBytes` → `GciStoreBytesInstanceOf`). `GciNativeExportTests` prüft über `GciNative.EntryPointNames()` (die `_Name`-Felder), dass jeder Einstiegspunkt in der Bibliothek existiert.
  - `GciLibraryResolver.cs` liefert die Kandidaten, `GciLibrary.cs` lädt einmalig per Pfad: unter .NET mit `NativeLibrary`, im net48-Build unter Windows mit `LoadLibraryExW(LOAD_WITH_ALTERED_SEARCH_PATH)`/`GetProcAddress`, unter Mono mit `dlopen`/`dlsym`. Die versionierte Datei (`.so`/`.dylib`/`.dll`, die höchste Version gewinnt) wird in dieser Reihenfolge gesucht: `GEMSTONE_GCI_LIBRARY` → `$GEMSTONE/lib` → `$GEMSTONE/bin` (Windows-Client) → Verzeichnis der Anwendung → OS-Suche.
  - `GciErrSType.cs` — blittable Spiegel der nativen Struktur mit Fixed Buffers; Offsets und Größe (2168 Byte) werden von `GciErrSTypeLayoutTests` abgesichert. Neue native Structs genauso anlegen und ebenso mit Layout-Tests absichern.
- `src/GemStone.Gci/` — öffentliche API: `GciSession` (`GciInit` einmal pro Prozess, `GciSetNet` + `GciLoginEx` mit `GciLoginFlags.Quiet` als Standard, `Dispose` → `GciLogout`) und `GciException` (aus `GciErr`).
- Die klassische GCI ist nicht thread-sicher und hat eine „aktuelle Session“ pro Prozess. Mehrere `GciSession`s sind trotzdem möglich: Jeder native Aufruf läuft unter dem prozessweiten Lock `GciSession.Sync` und hinter `Activate()`. `Activate()` wirft bei ausgeloggter Session und macht die eigene Session per `GciSetSessionId` zur aktuellen. Neue native Aufrufe immer hinter `Activate()` stellen. `SwitchTo()` (ohne Prüfung auf laufende Async-Operation) nur fürs Abfragen von Nb-Aufrufen und für `Dispose` verwenden. OOPs temporärer Objekte gehören zu ihrer Session.
- Async (`GciSession.Async.cs`): `GciNb*` starten, dann unter dem Lock `GciNbEndPoll(…, 0)` abfragen und außerhalb des Locks mit `Task.Delay` (1 → 32 ms) warten. In der Zwischenzeit arbeiten andere Sessions. Laufen N Sessions asynchron, laufen ihre Gems parallel (`SessionsExecuteInParallel`). Synchrone Aufrufe auf einer Session mit laufender Async-Operation → `InvalidOperationException`. Abbruch → `GciSoftBreak` → `OperationCanceledException`. Es gibt den Status `GCI_RESULT_HAS_ERROR = 3`, er steht nur in `gci.hf`.
- OOPs sind in der öffentlichen API der Typ `Oop` (`record struct` über einem `ulong`, gleiche Größe – `Perform` castet `Oop[]` direkt auf `OopType*`). Die Werte von `Oop.Nil`/`True`/`False`/`Illegal` stehen nicht im Handbuch, sondern stammen aus `gcioop.ht`.
- Ausführende Funktionen (`GciExecuteStr`, `GciPerform`, …) liefern bei Fehlern `OOP_NIL`, das aber auch ein gültiges Ergebnis ist. Deshalb bei `OOP_NIL` immer `GciErr` abfragen (`GciSession.CheckResult`). `GciErr` liefert jeden Fehler nur einmal. Nach einem fatalen Fehler ist die Session weg; `GciLogout` darf dann nicht mehr aufgerufen werden.
- `GciExecuteStr` kompiliert den C-String als 8-Bit-String, UTF-8 würde dabei verstümmelt. `Execute` schickt Nicht-ASCII-Quelltext deshalb als Unicode-String (`GciNewUtf8String_(…, utf8OrUnicode: true)` + `GciExecute`), **nicht als `Utf8`**. Der Compiler von 3.6.5, 3.6.8 und 3.7.2 scheitert an `Utf8`-Quelltext, sobald ein Block darin vorkommt (ab 3.7.5 behoben) (`| d | d := [:x | x]. 'ö' size` → „Internal logic error in compiler: ComStrmSetCursor“). Unicode-Quelltext geht auf 3.6 und 3.7. Text wird per `printString` → `encodeAsUTF8` → `GciFetchBytes_` geholt (`PrintString`).
- PureExportSet (Handbuch 1.4): Ergebnisse von `GciNew*`, `GciCreate*`, `GciPerform*`, `GciExecute*` und `GciResolve*` sowie alle OOPs eines `GciErr`-Berichts landen automatisch dort. Inhalte von Instanzvariablen (`GciFetch*Oops`) dagegen nicht. Zwischenobjekte immer mit `Release` freigeben (überspringt Specials). `ThrowIfError` gibt die Fehler-OOPs selbst frei. `ErrorsAndEvaluateDoNotGrowTheExportSet` misst das über `System hiddenSetSize:`.
- Nach nicht-fatalen Ausführungsfehlern ruft der Wrapper `GciClearStack(context)` auf, ein `GciContinue` ist danach nicht mehr möglich. `GciSession.SoftBreak()` nimmt bewusst keinen Lock, weil es aus einem anderen Thread kommt.
- `samples/GsRepl` ist eine kleine REPL für manuelle Tests (Strg+C = Soft Break, `\` am Zeilenende = Fortsetzung, `:commit`/`:abort`/`:q`).
- Gegentest-Muster: Wenn eine neue Absicherung (Release, Session-Umschaltung …) gleich grün ist, kurz deaktivieren und prüfen, ob der Test dann wirklich fehlschlägt.
- Bekanntes GemStone-Problem, kein Wrapper-Bug: Läuft die NetLDI mit deutschem `LC_NUMERIC`, scheitert `DateAndTime printString` mit „unexpected format“ (`ScaledDecimal>>_printAsDateAndTimeANSISecondsOn:` erwartet `.`). Abhilfe: NetLDI mit `LC_NUMERIC=C` starten.
- Ohne `GciLoginFlags.Quiet` (`GCI_LOGIN_QUIET`) schreibt `libgcirpc` beim Login eine Zeile `gci login: …` nach stdout.
- Laufen ohne `GEMSTONE`: Auf Linux lädt `libgcirpc` zur Laufzeit per `dlopen` noch `libssl-*.so` und `libkrb5-*.so` (verifiziert mit 3.7.5). Alle drei müssen neben dem Binary liegen.
- `GciSession` ist auf mehrere Dateien verteilt (`partial`): Kern/Execute/Perform in `GciSession.cs`, Wertumwandlung in `GciSession.Values.cs`, Transaktionen in `GciSession.Transactions.cs`, struktureller Objektzugriff (Instanzvariablen, indizierte Slots, Bytes, NSCs, `NewObject`, `ResolveSymbol`) in `GciSession.Objects.cs`. Indizes sind wie in Smalltalk 1-basiert.
- `GciResolveSymbol` liefert bei unbekanntem Namen `OOP_ILLEGAL` ohne `GciErr` (steht nur im Header). **GemStone-Leck 3.7.5:** `GciResolveSymbol` lässt bei jedem Aufruf einen String mit dem Namen im PureExportSet, auch bei unbekannten Namen (auch in 3.6.5, 3.6.8 und 3.7.2, in 3.7.6 behoben). `TryResolveSymbol` nutzt deshalb `GciResolveSymbolObj` mit einem eigenen String, den es wieder freigibt (`ResolveSymbolDoesNotGrowTheExportSet`).
- **Wertumwandlung:** `Oop` bildet die `GCI_*`-Makros (Tag-Bits aus `gcioop.ht`) in reinem C# nach: SmallInteger, Boolean, Character und die Typ-Prüfungen brauchen keinen Roundtrip. Alles andere läuft über GCI-Funktionen. `ToValue`/`FromValue` übernehmen die Zuordnung nil/bool/long/BigInteger/double/decimal/Rune/string/byte[]/DateTimeOffset/DateOnly/TimeOnly. Was nicht zuordenbar ist, kommt als `Oop` zurück. Feste Klassen-OOPs stehen in `KnownClasses` (aus `gcioop.ht`); `DateAndTime`, `Date` und `Time` stehen dort nicht und werden per Name aufgelöst. Date ↔ `DateOnly` über `asDays`/`fromDays:` (Tag 0 = 1901-01-01, proleptisch gregorianisch wie .NET); Time ↔ `TimeOnly` über `asMicroseconds`/`fromMicroseconds:`.
- Nichts über `printString` parsen, wenn es locale-abhängig ist. ScaledDecimal/Float drucken mit der Gem-Locale (`0,333`). `ToDecimal` rechnet deshalb serverseitig `(x * 10^scale) rounded`; `NewScaledDecimal` erzeugt ein Literal (`12.34s2`), das der Compiler locale-unabhängig liest.
- `GciNewDateAndTimePosix` und `GciFetchDateAndTimePosix` nutzen beide die Unix-Epoche (1970). Der Header-Kommentar „1900“ ist falsch (verifiziert mit `asPosixSeconds`). Die Auflösung ist Mikrosekunden.
- `GciCommit` liefert FALSE ohne `GciErr` → Konflikt (`TryCommit` = false, `Commit` wirft `GciTransactionConflictException`); FALSE mit `GciErr` → echter Fehler. Nach einem Konflikt muss vor dem Wiederholen ein `Abort` kommen. `RunInTransaction` macht genau das.
- Transaktionstests schreiben unter einem eindeutigen Schlüssel `GemStoneGciTest_*` in `UserGlobals` und räumen in `Dispose` auf. Konflikte werden mit einer zweiten `GciSession` im selben Prozess erzeugt. Übrig gebliebene Schlüssel findet man mit `(UserGlobals keys select: [:k | k beginsWith: 'GemStoneGciTest_'])`.
- Traversal (`GciSession.Traversal.cs`, `GciTraversal.cs`): Der Puffer liegt in eigenem nativem Speicher (8 Byte Header `allocatedBytes`/`usedBytes`, danach Object-Reports mit je 40 Byte Header plus Wertepuffer, auf 8 Byte ausgerichtet). Die Reports werden sofort in verwaltete `GciObjectReport`s kopiert. Ein Objekt, das größer als der Puffer ist, kommt als mehrere Teil-Reports mit steigendem `FirstOffset`; `GciTraversal` führt sie zusammen. `GciTraversal.ToValue` dekodiert Kernklassen (Strings in allen Breiten, Utf8, ByteArray, Float, Specials) ohne Roundtrip. `Oop.ToSmallDouble` ist aus `GCI_OOP_TO_SMALL_DOUBLE` portiert (8-Bit-Exponent, `1.0e100` ist keine SmallDouble).
- `GciClampedTravArgsSType` laut Header: `clampSpec, resultOop, travBuff, level, retrievalFlags, isRpc`. Das Handbuch nennt eine andere Reihenfolge und lässt `resultOop` weg. `isRpc` muss 1 sein (C++-Konstruktor).
- **Change-Feed und Replikat** (`GciChangeFeed.cs`, `Mapping/GsReplica.cs`, Nutzer-Doku `docs/programming-model.md#a-replica-that-follows-the-stone`): Ersatz für ein In-RAM-System mit Telegrammen. Notify-Sets taugen dafür nicht (RC-Collections werden nicht gemeldet, Signale sind nicht persistent).
  - Server: Smalltalk-Klasse `GciChangeFeed` (von `Install` angelegt, Methoden werden bei jedem `Install` neu kompiliert), `consumers` = `RcKeyValueDictionary` Schlüssel → `{RcQueue. Serial der Listener-Session}`. `publish:` legt ein Array in jede Queue (im Transaktionskontext des Schreibers), `ring` schickt nach dem Commit Signal 7301 an jede noch lebende Listener-Session, `take:` = `removeAll` der eigenen Queue, Ergebnis als Menge. Einträge halten die Objekte selbst, nicht OOP-Nummern (kein GC/OOP-Wiederverwendung, solange nicht abgeholt).
  - Parallele Schreiber: kein Konflikt (`ParallelWritersDoNotConflict`; im Benchmark 400 Commits von 2 Importern, 0 Konflikte, 0 verloren).
  - `GsReplica<T>`: lädt ohne `TrackChanges`, `ReaderWriterLockSlim` (Read-Lock für Leser, Write-Lock nur während `Refresh`), Update = Abort → Take → Refresh → `Changed`. Auslöser: Signal 7301 über den Listener und ein Timer (`PollInterval`).
  - **Der Commit der Entnahme läuft im Hintergrund** (`Task.Run(session.TryCommitAsync)`), das nächste Update wartet darauf und macht danach trotzdem `Abort` (die Sicht des Commits ist alt, sonst fehlen spätere Importe). Grund: Ein Commit mit Änderungen wartet auf das Transaktionslog (test376: ~6 ms). Synchron committet lag die Latenz bei 12 ms, mit 2 Commits im Pfad bei 15 ms; jetzt 6,8 ms Median, davon 5,7 ms der Commit des Importers. Unter Volllast (2 Importer, ~100 Commits/s) 12 ms.
  - `Refresh` schlug Besitzer von Collections vorher über `CollectionOwners()` nach, das bei jedem Aufruf alles kopierte (Replikat mit 825.000 Objekten: 122 ms statt 17 ms pro Update). Jetzt direkt in `_untrackedCollectionOwners`, Snapshots nur, wenn es getrackte Entries gibt.
  - Tests: `GciChangeFeedIntegrationTests` (Gegentest: ohne Türklingel wird `TheReplicaFollowsASmalltalkWriter` rot). Grün auf allen fünf Zielversionen.
- **Signale** (`GciSession.Signals.cs`, `GciSignalListener.cs`, Nutzer-Doku `docs/notifications.md`): Notify-Set (`System addAllToNotifySet:` → `signaledObjects`) und Session-Signale (`System sendSignal:to:withMessage:` → `signalFromGemStoneSession`). Erkenntnisse aus Versuchen (3.6.5 und 3.7.6):
  - Beide landen immer in ihren Queues. Gelesen wird per Smalltalk mit einem Block `[:ms | …]` (`ListenSource`): abort, Queues leeren, bei `ms > 0` und leeren Queues auf einer Semaphore warten (`waitForMilliseconds:`), Queues noch einmal leeren. `Poll` = `value: 0` (synchron), `WaitAsync`/`Start()` = `value: ms` nicht-blockierend (`PerformCapturingSignalsAsync` → `RunNonblocking(waitOnSocket: true)`).
  - **Warten auf den Socket statt Abfragen im Takt:** `GciNbGetNotifyHandle()` (unter dem Lock, nach dem Start des Nb-Aufrufs) liefert den Descriptor der Session; `GciPollSocketForRead(fd, 50)` ist laut Header thread-sicher und ohne Bezug zur aktuellen Session, läuft also per `Task.Run` außerhalb des Locks. Gemessen: Median 0,5 ms statt 1,5 ms (Abfrage alle 2 ms), CPU 0,33 s statt 2,4 s in 20 s. Normale `ExecuteAsync`-Aufrufe nutzen das (noch) nicht.
  - Gelesen wird die Signal-Queue mit dem Primitive `System _signalFromGemStoneSession` (`{serial. int. msg. numPending}` oder nil). **Nicht `signalFromGemStoneSession`** (deprecated): Es macht aus der Seriennummer eine `GsSession`, die ab 3.7 nil ist, wenn der Absender sich abgemeldet hat → MNU `#serialNumber`, der ganze Aufruf scheitert, und alles darin Gelesene ist weg (3.7.2, 3.7.5, 3.7.6; 3.6.x liefert noch eine Session). Aufgefallen, weil in der Latenzmessung immer das letzte Signal fehlte. `GsSession sessionIdOfSerial:` liefert für Abgemeldete in 3.7 0 (→ nil), in 3.6 eine Zeit lang noch die alte Nummer.
  - Notify-Set und Collections: Hinzufügen/Entfernen wird gemeldet, auch bei 100.000 Elementen (interne Knoten). **Nicht gemeldet: `RcQueue`, `RcKeyValueDictionary`, `RcIdentityBag`** (schreiben in Teile pro Session); `RcCounter`, `RcIdentitySet` schon (3.6.5, 3.7.6).
  - **Ein serverseitiges Warten wird durch Signale unterbrochen:** Bei eingeschaltetem Signalisieren (`InterSessionSignal enableSignalling`, `ObjectsCommittedNotification enableSignalling`) löst die VM während `Delay wait`/`Semaphore wait` eine Notification aus. Der Handler notiert sie, ruft `wake signal` und `e resume: nil` auf, das Warten endet sofort.
  - Die VM schaltet das Signalisieren nach jeder Zustellung selbst ab („must be resent“ im Kommentar von `enableSignalling`).
  - **Signalisieren nur während des Wartens einschalten** (`ensure:` schaltet es danach ab, der Konstruktor schaltet es mit `disableSignaled…Error` aus). Grund: Ein Signal, das bei eingeschaltetem Signalisieren eintrifft, während die Session untätig ist, kommt als GCI-Fehler 6008/6010 vom nächsten Aufruf. Das ist **nicht verlässlich**: Session-Signal, danach Commit-Benachrichtigung → nur Fehler 6008, das Session-Signal ist weg (weder Fehler noch Queue). Gegentest: `ASignalAndACommitArrivingTogether` wird rot. In allen fünf Zielversionen. Bei abgeschaltetem Signalisieren bleibt beides in den Queues.
  - Eine Notification ohne Handler beendet die ganze Ausführung mit 6008/6010 (`defaultAction` → `_signalToDebugger`). Deshalb liegt alles vom Abort bis zum Bauen der Antwort unter dem Handler.
  - **Soft Break ist in Smalltalk fangbar** (`on: Break do:`, Fehlernummer 6003). `Watch`/`Poll`/`Stop` unterbrechen ein laufendes Warten damit (`Exclusive`, `_interruptWait`). Der Block antwortet trotzdem mit dem bisher Gelesenen, es geht nichts verloren.
  - `GciPollForSignal` taugt nicht als Auslöser: Jeder normale Execute verbraucht den Hinweis, die Daten bleiben in den Queues. Nicht angebunden.
  - `CallCapturingSignals`/`TryCaptureSignal` fangen 6008/6010 trotzdem ab (Signale von vor dem Konstruktor, oder wenn jemand das Signalisieren einschaltet) und wiederholen den Aufruf. Bei einem eingefangenen Signal wartet der wiederholte Aufruf nicht (`ms = 0`), sonst käme das Signal erst nach `MaxWait` an.
  - `signaledObjects` leert sich beim Lesen. Der Listener sieht neue Objekte erst nach Abort (`Watch` bricht vorher ab, sonst Fehler 2106).
  - Der Text eines Signals muss ein Byte-`String` sein: Unicode-Strings und Utf8 lässt das Primitive scheitern (2258/2094). `SendSignal` schickt Nicht-ASCII über `String withAll:`, Zeichen > U+00FF → `ArgumentException`.
  - `Stop()` aus einem `SignalsReceived`-Handler, der ohne SynchronizationContext direkt auf der Schleife läuft, darf nicht auf die Schleife warten (`_raising`), sonst Deadlock. Tests mit xUnit haben einen SynchronizationContext: Für so einen Test `Start` per `Task.Run` aufrufen.
  - Tests: `GciSignalIntegrationTests`. Zwei Sessions im selben Prozess; `PollUntil`/`Within` mit Zeitlimit, weil Signale asynchron über den Stone laufen. `NoSignalIsLostUnderLoad` lässt den Sender per `ExecuteAsync` auf seinem Gem parallel senden. Latenzmessung mit getrennten Prozessen: siehe `docs/notifications.md`.
- **GemStone 3.6.x:** `GciOopToFlt_` gibt es erst ab 3.7. `ToDouble` fällt auf `GciOopToFlt` zurück (Fehler über `GciErr`), `GciNativeExportTests` führt es als optional. Sonst ist die Bibliothek für den Wrapper gleich, und alle Tests laufen.
- **GemStone-Bug 3.6.5–3.7.6: `GciFetchPaths` bringt die Gem zum Absturz** (SIGSEGV in `checkFetchPathOffset` → `om::FetchSize_c(obj=0x14)`), wenn ein Pfadschritt *von* einem Spezialobjekt (nil, SmallInteger …) ausgeht; die Session ist dann weg. `FetchPaths` geht deshalb Schritt für Schritt vor (ein Roundtrip pro Pfadtiefe) und prüft vor jedem Schritt lokal `IsSpecial`. `GciFetchPaths` nie direkt mit mehrstufigen Pfaden aufrufen. Ungültige Indizes oder Byte-Objekte sind dagegen sicher (liefern `OOP_ILLEGAL`).   - **Gespeichert, aber nicht committet:** Nach `SaveChanges` gelten die Snapshots als geschrieben. Ein `Abort` (auch nach einem Commit-Konflikt) nimmt die Änderungen auf dem Server zurück; ohne Gegenmaßnahme würde das nächste `SaveChanges` nichts schreiben, die Eingabe ginge still verloren.
    - Deshalb führt der Kontext ein Journal `_undo` (Snapshot-Änderungen bestehender Entities: `JournalProperty`, `JournalElements`). Er hängt sich nur, solange das Journal nicht leer ist, an das interne Event `GciSession.TransactionEnded`. `Commit`/`TryCommit`/`CommitAsync` melden true und leeren das Journal. `Abort`/`Begin`/`AbortAsync`/`BeginAsync` melden false (im `finally`), dann wird das Journal rückwärts angewendet.
    - Undo per Entity, nicht per Entry-Objekt: Ein Reload zwischen Save und Abort ersetzt den Entry.
    - Neue Objekte werden nicht zurückgenommen: Temporäre Objekte behalten über einen Abort hinweg ihren Inhalt (verifiziert mit 3.6.5 und 3.7.6), nur die Referenzen persistenter Objekte auf sie verschwinden.
    - `System abortTransaction`/`commitTransaction` in Smalltalk bemerkt der Kontext nicht.
    - `SaveChangesAndCommit(maxAttempts)` = `RunInTransaction(_ => SaveChanges())`, das bei einem Konflikt dadurch neu schreibt.
    - Tests: `GsUncommittedSavesIntegrationTests` (committet eine eigene Klasse `GsTxTestItem` und räumt in `Dispose` auf).
  - Geerbte Properties müssen vom deklarierenden Typ geholt werden, sonst fehlt bei `private set` der Setter (Reflection-Provider und Generator).
  - `SaveChanges`: Beim Laden (`TrackChanges`, Standard an) legt der Kontext pro Objekt und Property einen Snapshot an (OOP, Wert, bei Collections die Elemente). Die geladenen OOPs hält er per `GciSaveObjs` (`GciSession.Retain`) im Export-Set, bis `Dispose`/`Clear` sie freigibt. Ohne das könnte die Gem temporäre Objekte zwischen Laden und Speichern einsammeln. Eine Wurzel, die der Aufrufer per `Load(Oop)` übergibt, hält dagegen der Aufrufer.
    - Geschrieben wird nur, was vom Snapshot abweicht: Entities werden nach Referenz verglichen, alles andere nach Wert.
    - Neue Objekte entstehen per `new` auf der GemStone-Klasse.
    - Eine geänderte Collection wird in place gepatcht, nicht neu befüllt (Diff gegen den Snapshot):
      - geordnet (`List`/Array-Shape): gemeinsamer Anfang und gemeinsames Ende bleiben, die Mitte wird ersetzt. Op `4 target from removed inserted`; der Server nimmt `removeIndex:`/`add:beforeIndex:`. Bei SortedCollection, Bag und `from = 0` nimmt er `remove:ifAbsent:`/`addAll:`, bei Array den Umweg über eine OrderedCollection-Kopie plus `size:`.
      - ungeordnet (Set-Shape): Multiset-Abgleich, Op 4 mit `from = 0`.
      - Dictionary: Op `5 target removedKeys puts`. Bestehende Schlüssel behalten ihr Objekt (Symbol bleibt Symbol).
      - Folge: Nicht angefasste Elemente bleiben dieselben Objekte, und was andere nach dem Laden ergänzt haben, bleibt erhalten (`ServerSideChangesToOtherElementsSurvive`). Op 3 (befüllen) gibt es nur noch für neu angelegte Collections.
      - Geschachtelte Collections (`List<List<T>>`, `Dictionary<K, List<T>>`, `T[][]`): Beim Laden bekommt jede innere Collection einen eigenen `CollectionSnapshot` (`SnapElement.Nested`). Eine Ebene höher werden innere Collections nach Referenz verglichen; `PatchContents` patcht danach rekursiv die Inhalte. Dieselbe C#-Instanz behält ihr GemStone-Objekt, auch wenn sie innerhalb der äußeren Collection verschoben wird. Eine neue Instanz wird neu angelegt, die Klasse ergibt sich aus dem C#-Typ. Tests: `NestedCollectionsArePatchedInPlace`, `NewAndMovedInnerCollections`, `NewObjectWithNestedCollections`.
    - Strings und Enums, die Symbols waren, bleiben Symbols. Enums werden als Symbol mit kleinem Anfangsbuchstaben geschrieben (`#frozen`).
    - Ein Commit gehört nicht dazu.
    - **Geschrieben wird als ein Batch** (`SaveRun`): erst alles planen (Ops `1 class` = `new`, `2 target index value` = `instVarAt:put:`, `3 target items` = Inhalt ersetzen; Werte als Paar `kind payload`), dann `GciSession.StoreAndExecute`. Das sind `GciStoreTrav` (legt das Ops-Array, Strings, Utf8, Floats, ByteArrays mit vorab per `GciGetFreeOops` geholten OOPs an) und danach `GciExecuteStrFromContext` mit dem Ops-Array als `self` (`BatchSource`).
      - Symbols, Nicht-ASCII-Strings (`Utf8` → `decodeToUnicode`), LargeInteger, ScaledDecimal, Date, Time und DateAndTime wandelt erst der Server um (`kind` 2–8). Das Ergebnis ist ein Array aus allen erzeugten Objekten, gefolgt von allen umgewandelten Werten, in der Reihenfolge der Auswertung. Der Client vergibt die Indizes in derselben Reihenfolge, in der er die Ops schreibt.
      - Snapshots, Identity-Map und `_entries` ändern sich erst nach Erfolg (`_onSuccess`), siehe `AFailedBatchLeavesTheContextUnchanged`.
      - Messwert: 300 Accounts mit 2.700 Änderungen und 300 neuen Orders brauchen 10 statt 7.509 GCI-Aufrufe. Davon sind 6 der Batch selbst (`ManyChangesCostAFewRoundTrips`).
      - **`GciGetFreeOops` liefert pro Aufruf höchstens 100.000 OOPs** (alle fünf Zielversionen). Den Rest des Ergebnis-Arrays lässt es stillschweigend auf 0, steht weder im Handbuch noch im Header. Unabhängig von `GEM_TEMPOBJ_CACHE_SIZE` (gemessen mit 50 MB, 1 GB, 3 GB; pro Session setzbar über den Gem-Service `!@host#netldi:port!gemnetobject -T <KB>`). Die Store-Traversal scheitert dann mit Fehler 2106 („forward reference using the object identifier 0“). `GetFreeOops` holt deshalb in Stücken (`MaxFreeOopsPerCall`) und prüft auf 0 (`FreeOopsBeyondTheLimitPerCall`).

Die Linux-Bibliothek ist nicht betroffen, auch nicht über das Netzwerk (geprüft über die LAN-Adresse). `GetFreeOops` rundet deshalb auf ganze Blöcke (`FreeOopBlock`) und hält den Rest pro Session in `_freeOopPool` (freie OOPs bleiben der Session bis zum Logout zugeordnet). Gefunden beim ersten Windows-Test: Die Folge war ein „Internal protocol error“ (2231/2233) in späteren Aufrufen derselben Session.
      - **Nicht `GciStoreTravDo_`** (ein Roundtrip weniger): Es meldet die geänderten Objekte und verlangt dafür `GciDirtyObjsInit`, also Dirty-Tracking für die ganze Session (sonst Fehler 2086, auch mit `alteredNumOops = 0`).

    - `Oop.TryFromSmallDouble` ist die lokale Umkehrung von `GCI_OOP_TO_SMALL_DOUBLE`: Exponent 0x380–0x47F, aber 0x380 nur mit Bruchteil ≠ 0. Gegen `GciFltToOop` geprüft in `SmallDoubleEncodesLocallyLikeGciFltToOop`. `NewFloat` nutzt es auch.

- **NuGet:** Gemeinsame Paket-Metadaten (Autor, Lizenz, Repo, Version `VersionPrefix`/`VersionSuffix`, Source Link) stehen in `Directory.Build.props`. Dort ist `IsPackable=false` voreingestellt, Projekte schalten es selbst ein. Das Paket für die **klassische** GCI heißt **`Gs64Net.Gci`** (Namespace bleibt `GemStone.Gci`). Nicht `GemStone.*`: Das Präfix `Gemstone.` ist auf nuget.org für die fremden Gemstone-Bibliotheken der Grid Protection Alliance reserviert, Paket-IDs ignorieren Groß-/Kleinschreibung. Der Name des Nutzers soll nicht im Paketnamen stehen; als Autor (Authors/Copyright) steht er dagegen. Die thread-sichere GCI (`GciTs*`) kommt später als **eigenes Paket** (eigenes Projekt, `PackageId` `Gs64Net.Gci.ThreadSafe`) und erbt dieselben Metadaten.
  - Die Paket-README ist `src/GemStone.Gci/PACKAGE.md` (wird als `README.md` gepackt), nicht die Repo-README mit ihren relativen Links.
  - Mit `GenerateDocumentationFile` (CS1591 abgeschaltet, aber unvollständige `<param>`-Listen und mehrdeutige `cref` sind Fehler) und `EnablePackageValidation`.
  - Die GemStone-Client-Bibliothek ist nicht im Paket (Lizenz GemTalk, muss zur Server-Version passen).
  - `IsPublishable=false` in der Bibliothek, sonst scheitert `dotnet publish` auf `samples/GsRepl` (NETSDK1129, mehrere Ziele).
  - Geprüft mit einem frischen Projekt, das das Paket aus einem lokalen Ordner bezieht (net8.0 mit dotnet, net48 mit Mono). Für so einen Test einen eigenen `globalPackagesFolder` nehmen, sonst landet die Vorabversion im globalen Cache, und ein neu gebautes Paket mit gleicher Version wird ignoriert.

## .NET Framework 4.8 (net48)

- **Ziele:** Die Bibliothek baut für `net10.0`, `net8.0` und `net48` (`TargetFrameworks` im csproj; `TargetFramework` aus `Directory.Build.props` wird dort geleert). `net48` ist für bestehende WinForms-Anwendungen gedacht. Die müssen als **x64-Prozess** laufen, weil GemStone 3.7 nur 64-Bit-Client-DLLs liefert.
- **Pakete nur für net48:** `System.Memory`, `Portable.System.DateTimeOnly` (öffentliche `DateOnly`/`TimeOnly`), `PolySharp` (Compiler-Attribute) und die Referenz `System.Numerics`.
  - `System.Memory` immer auf der **neuesten** Version halten (zurzeit 4.6.3, Assembly-Version 4.0.5.0). .NET Framework bindet strong-named Assemblies exakt. Der net48-Testhost des Windows-SDK 10 verlangt `System.Memory` 4.0.5.0; mit 4.6.0 (4.0.2.0) brach `dotnet test` unter Windows mit `FileLoadException` (0x80131040) ab, bevor ein Test lief. Mono ignoriert solche Versionsunterschiede, unter Linux fällt das also nicht auf.
  - Das Testprojekt erzeugt für net48 Binding-Redirects (`AutoGenerateBindingRedirects` + `GenerateBindingRedirectsOutputType`, weil es eine Bibliothek ist). Solange alle Verweise dieselbe Version nennen, entsteht keine `.dll.config`.
- **Ersatzfunktionen:** `src/GemStone.Gci/Polyfills/NetFrameworkPolyfills.cs` (nur `#if !NET`):
  - statische Erweiterungsmember aus C# 14 (`extension(ArgumentNullException) { ThrowIfNull … }`, `Environment.TickCount64`, `Encoding.Latin1`, `decimal.Scale` …), dazu klassische Erweiterungen (`TryDequeue`, `TryAdd`, `Chunk`);
  - `ReferenceEqualityComparer`, `NativeMemory` und `Ascii` als interne Typen;
  - ein **öffentliches** `System.Text.Rune`, damit die API auf beiden Zielen gleich bleibt.

  Fehlt etwas Neues aus der BCL, zuerst hier ergänzen. `#if` im Code nur, wo es nicht anders geht (`GeneratedRegex`, `IReadOnlySet`).
- **Nicht auf net48 verfügbar:**
  - Standard-Implementierungen in Interfaces, deshalb `IGsTwoWayConverter` als eigenes Interface;
  - Range-Zugriff auf Arrays (`arr[..n]` braucht `RuntimeHelpers.GetSubArray`), stattdessen `AsSpan(0, n).ToArray()`;
  - `nint` → `nuint`-Casts.
- **Tests gegen den net48-Build:** Das Testprojekt bekommt `net48` nur unter Windows oder mit `-p:WithNet48Tests=true`, weil `dotnet test` net48 unter Linux nicht hosten kann. Unter Linux startet `tests/Net48Runner/run.sh` einen minimalen xUnit-Runner (Reflection: Fact/Theory, InlineData/MemberData, Klassen-Fixtures, async) mit Mono. Mono braucht dafür seine Facade-Assemblies (`System.Runtime.dll` …, Paket `mono-complete`); die Referenz-Facades aus `Microsoft.NETFramework.ReferenceAssemblies` lädt Mono nicht. Stand: alle 329 Tests grün unter Mono 6.8 gegen 3.7.6 (der generierte Code nimmt dort den Reflection-Zweig statt `UnsafeAccessor`). Mono ist aber nicht das echte .NET Framework; der endgültige Test ist ein Windows-Rechner.

## Verzeichnisstruktur

- `gemstone-c/` — Markdown-Konvertierung des Handbuchs *GemBuilder for C* (GemStone/S 64 Bit 3.7, Sept. 2023), aufbereitet für KI-Werkzeuge. **Nur lokal, nicht im Git-Repository** (Urheberrecht GemTalk, steht in `.gitignore`). In einem frischen Klon fehlt das Verzeichnis; dann direkt `$GEMSTONE/include/*.hf`/`*.ht` und das PDF-Handbuch nutzen.
  - `README.md` — Index aller Kapitel und aller Funktionen mit Einzeiler-Beschreibung. **Zuerst hier suchen**, statt Verzeichnisse zu durchlaufen.
  - `00-…06-*.md` — ein File pro Kapitel. Wichtig für den Wrapper: `03-building-gci-applications.md` (Linken gegen `libgcirpc`/`libgcilnk`), `05-compiling-and-linking.md`, `06-gembuilder-for-c-files-and-data-structures.md` (Header-Dateien, Typen und Structs wie `GciErrSType`, `GciObjInfoSType`, `GciTravBufType` — relevant für P/Invoke-Marshalling).
  - `07-gembuilder-c-function-reference/` — eine Datei pro GCI-Funktion bzw. Makro (`GciLogin.md`, `GCI_OOP_IS_SMALL_INT.md`, …); `00-overview.md` gibt den Überblick.
  - `08-gemstone-c-statistics-interface/` — GCSI-Funktionen (`Gcsi*`) für den Zugriff auf Shared-Cache-Statistiken.
  - Jede Datei beginnt mit einem Kommentar `<!-- Source: … PDF pages N–M -->`; Verweise "page N" sind als Links auf die jeweilige Datei umgesetzt.

## Hinweise für die C#-Anbindung

- Windows wird nur als Client unterstützt, und nur x64 (`GciSession.EnsureInitialized` prüft `Is64BitProcess`). Unter x64 gibt es nur eine Aufrufkonvention, die Header definieren nur `__declspec(dllimport)`; dieselben Funktionszeiger-Signaturen gelten also für Linux und Windows. `GCI_WINDOWS_CLIENT` setzt die Bibliothek selbst. Die Windows-Konsole muss für Nicht-ASCII-Zeichen auf UTF-8 umgestellt werden (siehe `samples/GsRepl/Program.cs`). Gegen einen echten Windows-Client ist das noch nicht getestet.

- Makros wie `GCI_OOP_IS_SMALL_INT`, `GCI_BOOL_TO_OOP` oder `GCI_CHR_TO_OOP` sind keine exportierten Funktionen; sie müssen in C# anhand der OOP-Bitkodierung nachgebaut werden (Details in der jeweiligen Makro-Datei).
- Die Dokumentation beschreibt die klassische (nicht thread-sichere) GCI (`gci.hf`); `gcilegacy.ht` enthält Definitionen, die nur dort und nicht in der thread-sicheren GCI genutzt werden.
